Amber Engine Handover

Amber's computing unit is becoming a self-contained engine: it takes a stored physical plan with every location resolved, reads and writes storage, keeps no execution metadata and calls no service during a run. This page says where that work stopped and how to pick it up.

04The plan-shape batch, not merged

Your decision of 17 November: what the compiler resolves belongs in the plan's operator block, at port level where it is about a port. Pieces 1-4 are done on feat/sce-step2-lane and its suites pass there.

  1. Every output port carries its storage location in the plan; the scheduler uses it and the engine builds none.
  2. What an operator reads from outside the run (files with their links, a listing, the CSV column limit) is in the operator's block and handed to the executor beside its descriptor. The hidden descriptor fields are gone, and no log line can print a link's signature.
  3. A compile is for editing or for a run; the "unavailable" placeholders are gone.
  4. Test fixtures are out of the production code; the link allow-list cannot be widened at run time.

Piece 5 (six small findings) is not started. Merging onto the main branch will conflict in the unit's services that later fixes rewrote. One judgment call to review: a scan's settings still hold the resolved file name, which schema inference and the Python export read. A plan at the listing cap (10,000 files) is about 9 MiB.

06Decisions

Made by you

  • Postgres leaves the unit completely; no backward compatibility.
  • Amber is a pure engine: a resolved plan in, storage reads and writes, no execution metadata, no service calls during a run.
  • Only the gateway reaches a unit; the Dashboard does not call units; no relay service.
  • Units are not tied to Kubernetes.
  • An execution's state lives in one place; data and metadata stay apart.
  • A namespace per execution comes in step 5.
  • 17 Nov: resolved locations in the plan's operator block, at port level.
  • 17 Nov: take the cleaner approach; the run compile moves into the compiling service.
  • 17 Nov: stop after step 3.

Still yours to decide

  • Step 3's six choices, built to my recommendations: verdicts only in the Postgres row; a six-field closing record; independent of the upstream result service (#9356); statistics every 30 s and one e-mail per run; a new run replaces earlier finished results on the same unit, plus expiry a day after the end; three cut parts stay out.
  • Whether a scan's settings should also stop holding the resolved file name.
  • Whether to propose steps 1-2 before step 3 ends. I recommend yes once the cleanup is verified: upstream moved 27 commits in three days.
  • Whether to file the upstream bugs below as issues.
  • When step 4 resumes: the four questions in its research notes.

07Upstream bugs found on the way

None caused by this branch.

  • PartitionRule.FirstInput follows hash-map order, not port order.
  • The R UDF's setter chain is wrong for more than one worker.
  • Checkpoints: a source worker read its channel's port too early (fixed on fix/checkpoint-on-source-worker); pyamber has no checkpoint handler; JVM workers cannot serialize their result writer threads (since #3295). Replay end to end stays unverified.
  • Helm chart: Chart.lock lists minio where Chart.yaml lists rustfs; Envoy Gateway is always installed; its GatewayClass hangs in Terminating after an uninstall; the release must be named texera; the language-server image is amd64 only.
  • access-control-service logs request headers and tokens at INFO, and has no PATCH handler.
  • The editor: a killed operator still says Running; the result table stays on page 2 after a re-run; a page opened during a run logs a TypeError when it ends.
